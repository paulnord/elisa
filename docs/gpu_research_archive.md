# ELISa GPU performance research archive

This archive preserves the November 2026 CPU and GPU experiments through milestone 46. The last measured implementation is commit `e4c97b31533ec299f7cc486e69f07835d65b779b`. The archive adds an index, early test results, a Colab replay notebook and an intermediate checkpoint. The measured machine, Ada, had a 16-core Ryzen 9 5950X and a 12 GiB GeForce RTX 3080 Ti. The workloads below used FP64.

## What improved

| Workload | Matched result on Ada | Interpretation for a future port |
| --- | --- | --- |
| Stock ELISa, 12° facets, 32 walkers, 12 steps | Original CPU fit fell from 27.14 s with one worker to 5.17 s with 16. At 16 workers, offloading surface integration took 24.53 s. Three runs per configuration. | ELISa already parallelized walker likelihoods. The GPU owner handled 5,838 synchronous phase packets per fit. Preserve the multicore CPU comparison. [Scaling study](ada_mcmc_scaling.md) |
| Native fine-mesh spectra, 32 walkers, two steps, 16 workers | Original CPU 133.01 s, optimized CPU 85.52 s, CPU plus cuBLAS 75.81 s. The sampler trajectory checks passed. | Exact spectral batching improved both paths. On the 1.5° native prediction, spectra accounted for 55.5% of profiled time and surface coverage for 2.9%. Mesh refinement exceeded the light-curve error budget at all 48 tested positions. [Spectra](ada_cublas_native_spectra.md) · [Mesh study](ada_native_mesh_refinement.md) |
| Curved-surface model, 16 workers, same 16 generation-two proposals | CPU with separate eclipse-phase blocks 2,437.6 s. Evaluating four shared phases once reduced CPU time to 1,953.4 s with identical normalized predictions. GPU fields with the same shared phases took 2,279.1 s. One run per configuration. | Reusing eclipse calculations saved 19.9% end to end on this model. Across both generations CPU and hybrid agreed on 32/32 sampler decisions. Native facets agreed on 16/32 at 12° and 30/32 at 6°. [Scientific results](ada_progress.md) · [Stage timings](hardware_characterization.md) |

The two native studies time different meshes and chain lengths. The curved model recomputes fields and checks sixteen numerical resolutions per in-prior proposal. Compare times within a row. The longest final chain had five transitions. Time to a converged posterior and effective samples per second at matched accuracy remain open.

## Replay on another machine

1. Check out the archive commit and create a working branch. The [native scaling reproduction commands](ada_mcmc_scaling.md#reproduction) set up ELISa with the repository's test data. They specify the model parameters, source path, thread limits, FP64 mode and device selection. Adapt CPU affinity to the physical cores available. For a quick CPU check, use that environment and run `python -m pytest -q tests/tests_experimental/test_compact_phase_union.py`.
2. Run the stock CPU baseline serially and at the best physical-core count for the new machine. Then run the optimized CPU and hybrid variants on the same starts. For fine-mesh spectra, the [cuBLAS build and run commands](ada_cublas_native_spectra.md#hardware-and-reproduction) include face-by-face, light-curve and posterior comparisons. Set the CUDA architecture for the target device.
3. To replay the exact three-way m046 timing comparison, use the [generation-one selection](ada_validation/archive/m046-generation1-selected.json) as input to `scripts.compact_cohort restore`. Restore it twice with `reference` and once with `gpu`, in three fresh directories. Follow the [m046 pool and comparison commands](experimental_gpu_backend.md) to run split CPU, shared-phase CPU and shared-phase GPU. The GPU-field run fills the per-walker fields before starting the host eclipse pool. The [m045 selection](ada_validation/background-m045-selected.json) starts one generation earlier.
4. Record cold start, warm likelihood time and elapsed time through the completed fit or durable checkpoint. Include compilation, transfers, synchronization and final output. Repeat in alternating order. Compare proposed coordinates, acceptance decisions, fluxes and posterior differences, then repeat the mesh or curved-model resolution check. For scientific throughput, run chains long enough to estimate convergence and effective samples per second.

## When hardware makes a retest worthwhile

**GPU arithmetic.** A device with higher sustained FP64 throughput is a candidate for the Planck spectra and FP64 matrix integration. Test those first against the optimized CPU spectral path. The eclipse kernel also uses double-precision roots and square roots with irregular control flow. Profile the two kernels separately. The original runs captured timings but lacked achieved FP64, cache and DRAM counters. A roofline profile on the new machine can distinguish arithmetic limits from data movement. [Nsight Compute profiling guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html)

**CPU processing.** Faster individual cores can help the host eclipse calculation in both implementations. More cores help when independent walkers are ready. The native scaling test had 16 concurrent proposals per half-step. In m045 the host interval averaged 15.8 busy cores with 16 CPU workers. For a larger machine, first repeat the original ensemble, then time a larger ensemble separately. Report physical cores, threads per worker and throughput for each. [Native scaling](ada_mcmc_scaling.md) · [Curved-model resource measurements](hardware_characterization.md)

**RAM and VRAM capacity.** The 16-worker m045 CPU pool peaked at 26.8 GiB host memory. Its hybrid host pool peaked at 12.0 GiB after GPU preparation. The sampled device peak during that field stage was 1,348 MiB. Extra RAM becomes interesting if additional independent CPU walkers would otherwise cause paging. Extra VRAM becomes interesting if it lets a complete batch of changing fields and eclipse data stay on the GPU across stages. Measure peak working set and the host trips eliminated at each batch size. [Resource measurements](hardware_characterization.md)

**Memory bandwidth and the host link.** Measure host DRAM bandwidth, device DRAM throughput and CPU–GPU transfer time separately. The m045 device negotiated PCIe 4.0 ×8 under load. Its 579.8 MB of field archives measure file output, so they cannot be used to infer PCIe bandwidth. More memory channels or HBM merit a rerun when the corresponding memory system is saturated. A wider link, coherent interconnect or persistent device buffers merit a rerun when transfers or synchronized returns consume a material share of the full fit. Measure call latency for small packets as well as sustained throughput. [Hardware evidence](hardware_characterization.md) · [STREAM host-memory benchmark](https://www.cs.virginia.edu/stream/) · [CUDA data-transfer guidance](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/#data-transfer-between-host-and-device)

**A break-even target for the current design.** In generation two of m046, the hybrid spent 2.8 s restoring starts, 561.8 s preparing GPU fields and 1,714.6 s in the host pool. Holding the other stages fixed, field preparation would have to fall below about **236 s**, roughly **2.4× faster**, to beat the 1,953.4 s CPU run. That interval includes launches, compilation, synchronization and archive I/O as well as device work. It is a target for the whole stage. A design that keeps the eclipse calculation on the device changes the balance and calls for a fresh full-fit measurement. [Timing ledger](ada_validation/background-m046.json)
